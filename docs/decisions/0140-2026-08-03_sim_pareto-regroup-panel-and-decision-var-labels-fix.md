# 0140 — A Pareto Regroup Panel (Free Axis/Grouping over Any Objective/Decision Variable) Plus a Decision-Variable Label Fix

**Date**: 2026-08-03
**Status**: ✅ accepted

---

## Background

The Opt tab's existing `ParetoChart.tsx` could only draw a fixed "first objective vs. second objective" scatter plot, with no way for the user to change axes or group solutions by some decision variable. The user wanted, without re-running the optimization, to freely choose any objective/decision variable as the X or Y axis, and optionally pick a third dimension to color-group by, in order to explore the trade-off structure already present in an existing `pareto_front`.

## Decision

### Decision 1: add `ParetoRegroupChart.tsx`, remapping the existing `pareto_front` locally on the frontend, with no new backend endpoint

The candidate fields for the X/Y/group dropdowns are uniformly assembled from `objectives` (`f0..`) and the decision variables (`x0..`); when the user switches a selection, this only does a local lookup/reorder/binning over the same `result.pareto_front` array, triggering no backend request and requiring no optimization re-run. This approach was chosen over having the backend offer a new "query by field" endpoint because each solution in `pareto_front` already carries its complete `f[]`/`x[]`; changing the axis or grouping is a pure presentation-layer reorganization, with no reason to add a network round trip for it.

### Decision 2: the discretization strategy for the grouping variable — group by value when there are ≤6 distinct values, otherwise bin into 5 equal-width bins

The grouping dimension can be either discrete (such as T3's days-combination index, whose values cluster in the single digits) or continuous (such as T1's `value`), so no single grouping method covers both cases. The corresponding value for `groupKey` is rounded to two decimal places and deduplicated; if the number of distinct values after dedup is ≤6, it's grouped directly by value (the discrete case, each value its own group, labeled like `variableName=value`); beyond 6, it's treated as a continuous distribution and cut into 5 equal-width bins from the minimum to the maximum (labeled like `variableName lo–hi`). 6 and 5 are empirical thresholds, not precisely derived — a legend with up to 6 groups is still readable, beyond that interval binning avoids a legend explosion.

### Decision 3 (a bug fix, not a new decision, found and fixed alongside this feature): unify the X/Y/group labels on `decision_var_labels`, not `regimen_event_labels`

During development, `ParetoRegroupChart.tsx` was initially found to name decision variables the same way the existing Solutions table (`SimOptTab.tsx`) does, using `result.regimen_event_labels` — this field is generated by **regimen event** count (`optimizer_engine.py:390`), but a single event's `optimize:` sub-block can declare several of `value`/`time_start`/`time_end`/`days_pool`/`date_range` at once, each expanding into its own independent decision-variable dimension (the `var_specs` in `optimizer_engine.py:97-157`). In other words, the event count and the decision-variable count (the length of `x[]`) often don't match, and once the index runs out of bounds the frontend can only fall back to meaningless ordinal labels like `x1`/`x2`. The backend already has a properly aligned field: `decision_var_labels` (`optimizer_engine.py:385-386`), generated dimension by dimension from `var_specs`, matching `x[]` exactly in both length and order, with `[time]`/`[time_end]`/`[days]`/`[date]`/`[date_end]` suffixes distinguishing different decision dimensions of the same variable. Switching to this field let `ParetoRegroupChart.tsx` and the Solutions table correctly display variable names instead of falling back to ordinals under multi-dimension events.
