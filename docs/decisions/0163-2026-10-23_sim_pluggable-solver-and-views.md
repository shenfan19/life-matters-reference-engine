# 0163 — Pluggable Solvers and Views: Simulation, Optimization and the Model Editor as Registered Parts

**Date**: 2026-10-23
**Status**: ✅ accepted

---

## Background

The engine had one way to advance a model through time and it was called directly from five places: the command line run, the GUI session batches, the Monte Carlo runs, the optimizer, and the tests. The optimizer reached into `ModelStructure.step()` through its own copy of the step loop. The GUI had three built-in views, Overview, Simulation and Optimization, and the model editor, all wired by hand into one component, while plugin views (ADR 0157) went through a separate path. Neither the computational core nor the built-in views could be replaced or extended without editing the code that uses them.

## Decision

**1. One solver interface.** `reference_engine/src/solver.py` defines `Solver` with `advance(model, schedules, step_size, n_steps, start_step, start_time, output_variables, sim_start_date)` and `run(...)`, which resets the model and returns the whole history. Every caller that moves a model forward asks `get_solver()` for the solver and no longer calls the step loop itself: `ReferenceEngine.run_simulation`, the Monte Carlo runs, the session batches of the GUI and `optimizer_eval._run_sim`. The optimizer and the simulator can no longer drift apart, because they share the same call.

**2. The reference solver keeps the old behaviour exactly.** `ReferenceSolver` wraps `advance_steps`, the fixed-step solver that evaluates equations in order. It is the gold standard other solvers are measured against. A test runs the old hand-written loop and the solver on the same model and requires the same history.

**3. Capabilities.** A solver lists what it provides: `evaluate`, `batch`, `gradient`, `snapshot`, `events`, `stochastic`. `find_solvers(required)` returns the registered solvers that have all of them, so an optimizer that needs gradients is only offered a solver that has them. Only the reference solver is registered. The registry exists so a second solver can be added without touching the callers.

**4. The optimizer asks for a solver by capability.** `optimizer_backends.BACKEND_REQUIRES` lists what each search method needs from a solver, and `run_optimizer` calls `pick_solver` with it. The optimization block or the GUI override may name a solver with `solver:`, and a named solver that lacks a needed capability is refused with the missing ones listed. The result records `solver: {id, version, capabilities}`, because published results and validation grades depend on the solver that produced them. `GET /api/solvers` lists the registered solvers.

**5. The workbench state is one hook.** `useWorkbench` (`gui/src/components/Simulator/useWorkbench.ts`) holds all the state, effects and handlers that used to sit in `Simulator/index.tsx`, and returns them as one object `wb`. `index.tsx` is the shell: model tree, view rail, plugin host, dialogs.

**6. Views are registered by being files.** A view is a file `gui/src/components/views/<Name>View.tsx` that exports `view: ViewDef = {id, labelKey, icon, order, component}`, where `component` takes `{wb}`. `registry.tsx` finds these files with `import.meta.glob` at build time. Overview, Simulation, Optimization and the model editor are registered this way, in `OverviewView`, `SimulationView`, `OptimizationView` and `BuilderView`. The shell draws `getView(centerTab).component`, and the rail takes its built-in buttons from `railViews()`. The model toolbar and the two control bars the views share are built in `views/toolbars.tsx`. The `center-tab-*` test ids and the deep links are unchanged. A new view needs no edit to the shell or the rail. A view that must run in isolation, or comes from someone else, stays a bundle plugin hosted in an iframe.

**7. The input signal is computed apart from the model.** `schedule_runner.compute_inputs(schedules, prev_time, next_time, sim_start_date)` is a pure function that returns what each controlled variable receives in a step window, as `{variable: [contribution, ...]}`: the day, date range and window filters, the single-step and multi-step windows, and the `delivery` rules of ADR 0131 and ADR 0132 all live there and nowhere else. An empty list means the variable is off for that step. `apply_inputs(model, signal)` writes a signal into a model with the same reset-then-add rule as before, and `apply_schedules` is the two calls in a row, so every existing caller behaves as it did. `input_trajectory(...)` gives the summed input of a whole run with no model, which is what a compiled or differentiable solver reads. A solver other than the reference one therefore does not re-implement the schedule semantics.

**8. One result form.** `reference_engine/src/result.py` defines `Trajectory`: the step numbers, the times, one list per variable, and the solver that produced it. `Solver.simulate` returns one, `Solver.run` is its per-variable history for the optimizer, and `rows()` gives back the one-dict-per-step form that sessions and CSV use. Simulation results, Monte Carlo results, session creation and optimizer results all carry `solver: {id, version, capabilities}`.

**9. A second solver, `fast`.** `reference_engine/src/solver_fast.py` runs the same fixed-step equations, in the same order and on the same input signal, over one flat list of values instead of the model's Variable objects, the asteval symbol table and the per-assignment history. The equations were already compiled to Python functions, so the saving comes from that bookkeeping, not from the evaluator: about 2.3 times faster over 35 library models of 20000 steps. A model it cannot run exactly, one with a step hook or an equation that did not compile, is handed to the reference solver. It leaves the model in the state the reference solver would, so a session can continue under either. The reference solver stays the default; `set_default_solver` switches it, and `solver:` in the optimization block or the override picks it for one optimization.

The conformance suite `test_verification/test_solver_fast.py` runs 101 models under both solvers to CSV and requires identical files, and compares the full histories of 20000 steps. A solver may be used for published results only while that suite passes for it.

**10. A compiled solver, `numba`.** `reference_engine/src/solver_numba.py` rewrites the equation expressions of a model into slots of a value array, generates one function for the whole run and compiles it with numba. The input signal comes from `compute_inputs` ahead of the run as an array. The compiled function is cached by its source, so the many evaluations of one optimization compile it once. It raises on division by zero and flags a value that is not finite, and a run that does either, or a model or expression numba cannot compile, is done again by the fast solver from the untouched model, so the Python semantics of a skipped assignment are kept. On 25 library models of 20000 steps, with the compile already paid, it took 30 percent of the reference solver's time and never needed the fallback. It matches the reference solver to a relative 1e-9 over the same 101 models, with schedules, and a model that divides by zero gives the same file under all three solvers. numba is optional and listed in the requirements as a comment; without it the solver is not registered.

**11. Choosing a solver.** `--solver ID` on `lm-sim` and the environment variable `LM_SOLVER` set the default solver of a process, so the API server picks it up too. An optimization names its own with `solver:`. The default stays `reference`.

**12. Reading the schedules once.** Profiling an optimization showed that four fifths of its time was `compute_inputs` re-reading the time strings and date ranges of the schedules at every step. `schedule_runner.InputSignal(schedules, sim_start_date)` now does that once and `at(prev_time, next_time)` answers for a step window, with the answer shared between windows that have the same time of day and weekday. `compute_inputs` is `InputSignal(...).at(...)`, and every solver reads the signal this way. `test_input_signal_equivalence.py` keeps the previous step-by-step implementation as a frozen copy and compares the two on 240 random schedule sets. With this and an array-based trajectory for the compiled solver, an optimization of 30 evaluations by 3 generations on the all-tiers fixture took 18 seconds on `numba` against 47 on `reference`.

**13. Choosing a solver in the GUI.** The toolbar shows a selector when the backend lists more than one solver (`GET /api/solvers`). The choice is kept in the browser (`lm_solver`), goes into the start request of every simulation (`solver`) and into the optimizer override, and a session keeps the solver it was started with. Without a choice the server default applies. The selector is disabled while a run is going.

**14. Snapshot and restore.** Every solver provides `snapshot(model)` and `restore(model, snap)`, the state a run can be resumed from (values, step count, time), and declares the `snapshot` capability. A branch of the future can be tried, the model put back and another tried, which receding-horizon control and tree search need. A test checks that the replay after a restore equals the first run on all three solvers.

**15. Not done.** A differentiable solver needs JAX or a similar library, which is not a dependency of the engine; the `gradient` capability has no provider yet, so a gradient method would find no solver. The `batch` capability has none either. Bundle plugins for the simulation, optimization and editor views would need a message protocol for result streams and a write contract with a trust model, which ADR 0157 left open; they stay registered views.

**16. Not changed.** The meaning of the equations, the input semantics of ADR 0131 and ADR 0132, and the result format. A second solver has to reproduce the reference solver within a tolerance before it may be used for results that are published.
