# 0061 — Stage intermediate results in models/temp/, no user account system

**Status**: 📋 Decided
**Date**: 2026-05-06

## Background

Simulation/optimization runs produce intermediate files: the input override written back from an opt result, staged parameter overrides, generated charts.
The original `users/` directory was designed for a multi-user cloud service (account isolation, saves, optimization history), which badly overshoots the current MVP goal (publish a paper, run a local demo).
Removing `users/` requires a lightweight replacement so a browser refresh doesn't lose intermediate results.

## Decision

Use `models/temp/{job_id}/` as a session-scoped staging area, with no user account system:

```
models/temp/
  {job_id}/
    input_override.yaml   # the new input written back from an opt result (can be fed straight into sim)
    charts/               # generated chart files
    result.csv            # sim/opt output
```

- `job_id` is generated by the backend (uuid) when a job is created, and returned to the frontend
- The frontend stores `job_id` in `localStorage`, so it survives a refresh
- On startup, the backend cleans up temp directories older than N hours (suggested: 24h)
- Users can download any file via `GET /api/download/result/{job_id}`
- An opt result YAML can be used directly as the input for a new scenario, or renamed by the user and moved to `models/scenarios/`

Also removed:
- the `users/` directory (entirely)
- `tools/update_yaml_steps.py` (a one-off migration script)
- stale migration/run scripts under `script/` (listed below)

## Consequences

- ✅ No need to implement auth, account isolation, or cloud storage
- ✅ Refresh-safe: the job_id persists in localStorage, so intermediate results aren't lost
- ✅ The backend already knows the models/ path, so no new configuration is needed
- ✅ Substantially less code, keeping focus on the MVP
- ⚠️ Under multi-user concurrency, temp directories could collide (no impact for a single-machine demo; needs isolation before going live)
  → **2026-05-18 revision**: upload-temp is now an atomic operation (UUID prefix, deleted after the request completes); the concurrent-upload collision problem is resolved (see ADR 0077)
- ⚠️ temp is wiped on server restart, so users need to be told to download promptly
  → the upload-temp result is now returned to the frontend and stored in localStorage, so the temp directory is no longer used persistently; this warning now applies only to simulation session data
