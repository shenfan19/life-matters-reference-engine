# SCS Deployment Guide (a public-internet demo server)

For deploying a public-facing demo instance of this engine on a cloud host such as DigitalOcean.
This document assumes you are not experienced with Linux server administration, and is written in the actual order of execution — just follow along; a brief explanation precedes each step's concept.

---

## 0. Prerequisite concepts

- **systemd**: Ubuntu's built-in process manager. The backend is a Python program that needs to keep running, and systemd handles "auto-starting it after a server reboot, auto-restarting it if the process crashes, and providing a unified start/stop/log-viewing command," so you don't need to babysit a terminal.
- **Nginx**: a reverse proxy. The backend only listens on `127.0.0.1:18080` (unreachable from outside, safer), and the frontend is a set of built static files. Nginx exposes port 80 to the outside uniformly: when a webpage file is requested, it serves the file directly; when `/api/...` is requested, it forwards to the backend on port 18080 — a visitor only needs to visit `http://<server IP>/`, with no need to know the backend's port number.
- Both are auto-configured by `scripts/scs_setup.sh`; there is no need to hand-write a configuration file.

## 1. Preparing the server

1. Create a droplet on DigitalOcean, choosing the **Ubuntu 22.04/24.04 LTS** image, and a spec of 1 vCPU / 1GB memory is enough to start with (you can temporarily upgrade the spec when running a simulation/optimization that's resource-hungry; DO bills by the hour)
2. SSH into it (the DO console will give you a root password or let you set up an SSH key)
3. Install git: `sudo apt update && sudo apt install -y git`

## 2. Fetching the code (the two repositories must sit side by side under the same parent directory, not nested)

```bash
mkdir -p ~/life-matters && cd ~/life-matters
git clone <the life-matters-reference-engine repository URL>
git clone <the life-matters-models repository URL>
```

This gives:

```
~/life-matters/
├── life-matters-reference-engine/
└── life-matters-models/
```

## 3. Running the one-shot install script

```bash
cd ~/life-matters/life-matters-reference-engine
chmod +x scripts/scs_setup.sh
sudo bash scripts/scs_setup.sh
```

This step automatically does the following: install nginx/python/node -> create the Python virtual environment `.venv` -> install backend dependencies (`reference_engine/requirements.txt`) -> build the frontend static files (`gui/dist/`) -> write `.env` (`LM_MODELS_PATH` pointing to `life-matters-models/models`, `SCS_MODE=true` forbidding a public visitor from writing server files, `LM_MAX_CONCURRENT_OPTS/SIMS` capping concurrency to prevent overloading the server) -> write the systemd service `lm-backend` -> write the Nginx reverse-proxy configuration (including an English "under maintenance" placeholder page, `lm-test`, used together with `scs_toggle.sh test/live` when temporarily taking the site offline) -> open firewall ports 22/80/443.

**If you have a domain**: before running it, edit the `SERVER_NAME` variable at the top of `scripts/scs_setup.sh` to your domain name; if you're only accessing it by IP, no change is needed (keep `_`).

After it finishes, visit `http://<the server's public IP>/`, and you should see the frontend page.

## 4. Day-to-day operations

| Need | Command |
|---|---|
| View the backend's live log | `journalctl -u lm-backend -f` |
| Check whether the backend is running normally | `systemctl status lm-backend` |
| Restart the backend | `sudo systemctl restart lm-backend` |
| Restart Nginx (after changing its config) | `sudo systemctl reload nginx` |
| Turn public access off/on | `bash scripts/scs_toggle.sh off` / `bash scripts/scs_toggle.sh on` |
| Switch to the maintenance placeholder page / switch back to the real app | `bash scripts/scs_toggle.sh test` / `bash scripts/scs_toggle.sh live` |
| Check the cumulative visit count (private, see below) | Open `http://<IP or domain>/api/stats/<LM_STATS_TOKEN>` in a browser |

**Visit counting**: each time the homepage loads, it makes one request to the backend's `/api/visit`, which accumulates a per-day count written into the server-local `output/visit_count.json` (dated by the server's local time, UTC by default on DO); it records no IP, cookie, or any information that could identify a visitor. The count is viewed privately via `LM_STATS_TOKEN` in `.env` (auto-randomly generated by `scs_setup.sh` during setup, with the complete query URL printed in the setup log; save it yourself, don't share it), with no account login; `/api/stats/<token>` returns `{"total": total count, "by_day": {"2026-09-04": 3, ...}}`, plain-text JSON, sorted by date. If the URL is never visited, no one knows it exists, and a mismatched `token` always returns 404, so the existence of this stats endpoint itself is never revealed.

## 5. Redeploying after a code update

```bash
cd ~/life-matters/life-matters-reference-engine
git pull
sudo bash scripts/scs_redeploy.sh
```

This reinstalls any changed backend dependencies, rebuilds the frontend, and restarts `lm-backend`. **There's no need** to rerun `scs_setup.sh` — the nginx/systemd configuration is one-time and is already running.

## 6. Troubleshooting

- **The webpage won't load**: check `systemctl status lm-backend` to see whether the backend is running; run `sudo nginx -t` to check the Nginx configuration syntax; run `sudo ufw status` to confirm port 80 is actually open.
- **The backend fails to start**: run `journalctl -u lm-backend -n 50` to see the last 50 log lines — this is usually a missing dependency (rerun `.venv/bin/pip install -r reference_engine/requirements.txt`) or a wrong path in `.env`'s `LM_MODELS_PATH`.
- **A change to `.env` has no effect**: `.env` is only read once, when the backend starts; after editing it, run `sudo systemctl restart lm-backend`.

## Difference from local development

Trying it out locally (`./run.sh` / `run.cmd`) and this deployment **are not the same thing**; the specific differences:

| | Local `run.sh`/`run.cmd` | SCS deployment |
|---|---|---|
| Frontend | `npm run dev`, occupying a process continuously, hot-reloading | Built once (`npm run build`), then pure static files, served directly by Nginx, no frontend process needs to stay running |
| How the backend stays alive | Runs in the foreground, stops when you close the window/Ctrl+C | systemd keeps it running, auto-recovering on restart/crash |
| Write permission | It's just you locally, unrestricted | `SCS_MODE=true`, forbidding a public visitor from writing server files |
| External exposure | Only on `localhost`, unreachable from outside | The backend still binds only `127.0.0.1`; Nginx proxies it open to the public |

`run.sh` can also run on the server (e.g. to manually verify things by hand after setting up the environment), but that's only a one-off smoke test, not a way to keep the service running externally.
